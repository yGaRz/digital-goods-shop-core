# E2. Exactly-once под гонками

**Задачи:** T2.1–T2.5 · **~4 ч** · [S3](../сценарии.md#s3-50-одинаковых-event_id), [S4](../сценарии.md#s4-50-разных-event_id-на-один-заказ), [S5](../сценарии.md#s5-вебхук-раньше-заказа), [S17](../сценарии.md#s17-failed-после-paid)

## Зачем это учим

Платежка гарантирует **at-least-once**, не exactly-once. Exactly-once — наша работа: уникальность события + блокировка заказа + терминальный статус.

Это другой класс гонки, чем S20 (пять заказов) и чем 200 покупателей на 30 ключей (E4b). Здесь бьют **один** заказ.

## Сущности и значения

| Что вводим | Смысл | Дефолт | Где пригодится |
| --- | --- | --- | --- |
| `UNIQUE(event_id)` | одно событие — одна обработка | уже желательно с E1c | S3 |
| `SELECT FOR UPDATE` заказа | два вебхука не видят оба `created` | | S3/S4, потом worker E4a |
| `POST /payments/burst` | 50 параллельных HTTP | режимы same / distinct event_id | приёмка ТЗ п.1–2 |
| буфер события до заказа | out-of-order | 200, не 5xx | S5 |
| late `failed` | не откатывает `paid`/`delivered` | лог, игнор FSM | S17 |

## Что должно щёлкнуть

- Один `event_id` × N = одна обработка (S3).
- N разных `event_id` ≠ N выдач (S4).
- Событие раньше заказа (S5). Тест в одном потоке с lock не доказывает гонку (P20).

## Сделать

UNIQUE + блокировка, burst двух режимов, буфер orphan-вебхука, параллельный автотест, S17.

## Проверить

S3, S4, S5, S17. После S3: одна выдача, один settle-ключ. После S4: 50 строк payment_events, один delivered. Kibana: 50 webhook, один issue.
