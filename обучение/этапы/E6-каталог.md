# E6. Каталог под нагрузкой

**Задачи:** T6.1–T6.3 · **~3 ч** · [S15](../сценарии.md#s15-горячая-витрина-остатков)

## Зачем это учим

Не платежи, но типичный соседний контур маркетплейса: витрина остатков не должна делать тяжёлый COUNT на каждый хиты главной. Нужно увидеть план запроса, не «добавить Redis наугад».

## Что должно щёлкнуть

- «Горячий» запрос = фиксированный доступ (по in_stock, сортировка, limit), не полный dump каталога.
- Индекс под предикат; иногда счётчик остатка на `products`, обновляемый при выдаче (тогда витрина не ходит в keys).
- EXPLAIN — артефакт обучения, его кладут в записку.

## Сделать

Seed 1000+ SKU, `GET /catalog/stock`, индекс(ы), текст EXPLAIN.

## Проверить

S15. Сравнить EXPLAIN до и после индекса (сохранить оба плана в этап или в записку).

## Разобрать

- P18 COUNT без индекса  
- Связь с E4: выдача ключа должна обновлять то, что видит витрина, иначе витрина врёт  

Вопросы себе:

1. Витрина читает `keys` или денормализованный `products.available`? Какой инвариант с S9?
2. Нужен ли Elasticsearch для поиска по имени (в ТЗ не обязательно) vs Postgres для остатка?

## Антипаттерн ИИ

Кэш без инвалидации после выдачи последнего ключа — витрина продаёт пустоту.
