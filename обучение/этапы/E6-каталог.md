# E6. Каталог под нагрузкой

**Задачи:** T6.1–T6.3 · **~3 ч** · [S15](../сценарии.md#s15-горячая-витрина-остатков)

## Зачем это учим

Это уже не платежи, а соседний кусок витрины: список «что есть в наличии» не должен на каждый заход тяжёло пересчитывать весь запас.  
Нужен понятный план запроса к базе, а не «давайте сразу Redis наугад».

## Простыми словами: что добавляем

| Что | Зачем простыми словами | Как у нас | Потом |
| --- | --- | --- | --- |
| ≥1000 товаров | Нагрузка на «горячий» список | поверх 12 учебных из задания | план запроса в записке |
| Витрина остатков | Фиксированный доступ (есть/нет, сортировка, лимит), не выгрузка всего | `GET /catalog/stock` | |
| Индекс или заранее посчитанный остаток | Витрина не делает тяжёлый COUNT по ключам поставщика каждый раз | выбрать одно, описать связь с выдачей | после шторма витрина не врёт |

12 учебных SKU остаются; тысячи — синтетика для нагрузки.

## Что должно стать ясно

- Горячий запрос = понятный фильтр + индекс.
- План запроса (EXPLAIN) — артефакт обучения, его сохраняем.

## Сделать

Seed 1000+, endpoint витрины, индекс(ы), текст EXPLAIN до/после, API docs.

## Проверить

S15. Сохранить оба плана запроса.
