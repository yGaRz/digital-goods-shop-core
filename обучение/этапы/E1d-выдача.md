# E1d. Seller A — выдача ключа и разнос денег

**Задачи:** T1d.1–T1d.5 · **~2.5 ч** · [S1](../сценарии.md#s1-happy-path), [S18](../сценарии.md#s18-повтор-создания-заказа)

## Зачем это учим

После E1c магазин знает: «деньги за заказ пришли» и держит их **на удержании**. Ключа у покупателя ещё нет, поставщику мы ничего не должны.

На E1d появляется **поставщик (Seller A)** с запасом кодов. Магазин запрашивает код, записывает его в заказ и только тогда в журнале денег:

- снимает сумму с удержания;
- часть «должны поставщику» (например 450 из 500);
- часть «комиссия магазина» (10%, например 50).

Важно разделить два момента:

1. Банк прислал «оплачено» → ответ банку должен быть **быстрым** (просто приняли факт оплаты).
2. Долгий запрос кода у поставщика → **не внутри** этого ответа, а фоном (очередь задач + обработчик). Иначе банк решит, что уведомление не дошло, пришлёт его снова — и при пятидесяти повторах начнётся путаница с выдачей.

Один и тот же код нельзя отдать двум заказам. Деньги поставщику — **после** того, как уникальный код уже привязан к заказу, а не в момент «оплачено».

Seller B на этом этапе **не** поднимаем.

## Простыми словами: что добавляем

| Что | Зачем простыми словами | Как у нас называется | Потом пригодится |
| --- | --- | --- | --- |
| Сервис поставщика A на порту 8083 | Лежит запас сырых кодов; по запросу отдаёт один код | Seller.Api, контейнер A | S1, потом несколько покупателей и шторм |
| Запрос «выдай код» | Магазин просит код для заказа; повтор с тем же номером запроса → тот же код | `POST /issue` | таймауты и повторы позже |
| Стабильный номер запроса к A | Не новый случайный id на каждый повтор, а один и тот же | `request_id = req_{orderId}:A` | чтобы повтор не выдал второй код |
| Очередь «надо выдать» + фоновый обработчик | Сначала сохранили оплату и ответили банку; выдачу делает отдельный цикл | outbox + worker | 50 одинаковых уведомлений об оплате; дожим зависших |
| Комиссия 10% отдельной строкой в журнале | Не «в уме 500−10%», а явная запись | счёт `platform_fee` | сверка денег |
| «Должны поставщику A» | Учётный долг после выдачи кода | счёт `seller_payable:A` | не путать с поставщиком B позже |
| Код в заказе, уникальный | Факт «этот код ушёл в этот заказ» хранит магазин | `orders.code` UNIQUE | нельзя двум заказам один код |
| Заголовок при создании заказа | Двойной клик «Купить» не создаёт второй заказ | `Idempotency-Key` | S18; в шторме у разных покупок ключи разные |

Пул кодов до выдачи принадлежит **поставщику**. Магазин хранит только факт: какой код попал в какой заказ.

## Что должно стать ясно

- Полный путь одной покупки: создать заказ → оплата → код → в журнале три фазы (удержание, потом разнос поставщику и комиссии).
- Выдавать код можно только если заказ уже «оплачен» (или идёт выдача) — не из «ещё ждём оплату».
- Ответ банку и поход к поставщику — **разные** шаги по времени.

## Сделать

- Seller A в docker-compose, запас кодов A (без пересечения с будущим B), health на :8083.
- Таблица/очередь outbox + worker в Shop: после успешной оплаты ставит задачу на выдачу; вебхук **не** вызывает поставщика сам.
- Вызов `/issue`, запись кода в заказ, проводки разноса денег, `GET /orders/{id}` отдаёт код.
- `Idempotency-Key` на создание заказа (S18).
- Черновик сверки балансов по заказу (после S1 расхождение = 0).
- Обновить [Api docs](../../Api%20docs/API%20DOCS.md).

## Проверить

- Прогнать **S1** (счастливый путь до кода) и **S18** (повтор создания заказа с тем же ключом идемпотентности).
- В SQL посмотреть строки журнала денег этого заказа: сначала удержание, потом разнос.
- В логах/Kibana цепочка: покупка → уведомление банка → запрос кода → разнос денег.
