**Задачи:** T4a.1–T4a.2 · **~2.5 ч** · [S10](../сценарии.md#s10-оплачен-не-выдан), [S11](../сценарии.md#s11-выдан-не-оплачен-должно-быть-0), [S12](../сценарии.md#s12-дожим-после-пополнения)

## Зачем это учим

«Оплачен / не выдан» должна находиться запросом, не grep логов. Шторм рано: сначала сверка должна врать или сходиться на **одном** застрявшем заказе, иначе 200 строк скроют формулу.

## Сущности и значения

| Что вводим | Смысл | Дефолт | Где пригодится |
| --- | --- | --- | --- |
| `GET /admin/reconcile` | операционная правда | imbalance=0 после S1/S20 | S9 глазами JSON, Grafana E5 |
| «paid без code» | деньги в escrow или refund_pending | | S10 |
| «delivered без paid» | всегда пусто | | S11, P15 |
| `POST /admin/retry-stuck` | дожим восстановимых | тот же request_id, `settle:{orderId}` | S12, не трогает delivered |
| переход RefundPending → payable+fee | эскроу уже пуст после OOS | P22 | S12 и потом хвост шторма |

Прогонять на 1–N заказах (оборвать селлера / маленький seed), не на 200.

## Что должно щёлкнуть

- Сверка статусов ≠ сверка денег (P12). `bank = escrow + payable + fee + refund`.
- Worker не берёт `delivered` / `payment_failed`.

## Сделать

Reconcile API, retry-stuck, S10–S12 на малом.

## Проверить

JSON imbalance 0 после S1. S10 список не пуст, когда надо. S11 пуст. S12 после доливания ключей: delivered вырос, refund упал, повторный retry безопасен.
