# Сценарии и проблемы

Проверяемые прогоны (**S**) и типичные поломки (**P**). Ожидание — что должно быть. «Сломано если» — сигнал, что инвариант не понят. После прогона смотреть Kibana (`order_id`) и Grafana (статусы, 5xx, imbalance).

Связь с этапами: колонка «Этап». Задачи кода — в [АРХИТЕКТУРА.md](../АРХИТЕКТУРА.md) §7.

---

## Как гонять

1. Поднять compose (этап E0).
2. Seed: каталог, ключи, `faults=0`, если не сказано иное.
3. Выполнить шаги сценария из Postman (когда коллекция появится — те же имена).
4. Сверить «ожидание» и reconcile.
5. Если разошлось — найти **P** ниже, не чинить вслепую.

---

## Сценарии

### S1. Happy path

**Этап:** E1. **Учим:** заказ → оплата → эскроу → выдача → settlement.

1. `POST buyer /purchases` SKU из каталога.
2. `POST bank /payments` `{ orderId, status: "paid" }`.
3. `GET shop /orders/{id}`.
4. `GET shop /admin/reconcile`.

**Ожидание:** статус `delivered`, один `code`, ledger сходится: эскроу 0 по этому заказу, селлеру +(amount−fee), `bank_asset` +amount.

**Сломано если:** код есть, а селлеру не начислено; селлеру начислено на шаге 2 до выдачи; два кода.

**Разобрать:** [P2](#p2-settlement-на-вебхуке), [P14](#p14-выдача-внутри-http-вебхука-без-outbox).

---

### S2. Оплата не прошла

**Этап:** E1.

1. Создать заказ.
2. Вебхук `status: "failed"`.

**Ожидание:** `payment_failed`, ключа нет, эскроу нет, селлеру 0.

**Сломано если:** вызван `/issue`; статус `delivered`.

**Разобрать:** [P15](#p15-выдача-до-paid).

---

### S3. 50 одинаковых event_id

**Этап:** E2. **Учим:** at-least-once доставка вебхука.

1. Заказ `created`.
2. `POST bank /payments/burst` `{ orderId, count: 50, mode: "same_event_id" }`.
3. Reconcile + GET order.

**Ожидание:** все 50 ответов 200; один `delivered`; один settlement; один код.

**Сломано если:** 50 выдач, 50 ключей, N settlement, 5xx на части запросов из-за гонки без блокировки.

**Разобрать:** [P1](#p1-check-then-act), [P3](#p3-нет-unique-event_id).

---

### S4. 50 разных event_id на один заказ

**Этап:** E2. **Учим:** идемпотентность заказа, не только события.

1. Burst `mode: "distinct_event_id"`.

**Ожидание:** 50 событий в `payment_events`, **одна** выдача. Повторные paid не оживляют финальный заказ.

**Сломано если:** второй event_id после `delivered` снова зовёт селлера.

**Разобрать:** [P4](#p4-идемпотентность-только-event_id).

---

### S5. Вебхук раньше заказа

**Этап:** E2. **Учим:** out-of-order.

1. `POST /payments` с несуществующим `orderId` (или id, который создадите следующим шагом — заранее известный).
2. Затем `POST /orders` с тем же id **или** создать заказ и слать вебхук с этим id, инвертировав порядок как в реализации (зафиксировать в этапе E2).
3. GET order.

**Ожидание:** событие не потеряно; после появления заказа он доходит до `delivered` (если paid). Нет 500 «order not found» как финального состояния.

**Сломано если:** вебхук ответил 5xx и банк бесконечно ретраит без буфера; заказ навсегда `created`.

**Разобрать:** [P5](#p5-вебхук-500-если-заказа-нет).

---

### S6. Таймаут, но код выдан

**Этап:** E3. **Учим:** таймаут ≠ отказ.

1. `PUT seller-a /admin/faults` `{ "timeoutRate": 1, "timeoutSeconds": 30 }` и логика «сначала резерв кода, потом sleep».
2. Shop timeout клиента короче sleep (например 2 с).
3. Оплатить заказ.
4. Дождаться retry.

**Ожидание:** один `code`, тот же `request_id` в логах дважды, второй ответ с тем же code. Селлеру один settlement.

**Сломано если:** два разных code; выдача с A и с B; ключ «завис» без заказа.

**Разобрать:** [P6](#p6-таймаут--отказ), [P7](#p7-новый-request_id-на-retry), [P8](#p8-fallback-после-таймаута).

---

### S7. Fallback A → B

**Этап:** E3.

1. A: `errorRate: 1` (явный 5xx, без резерва кода).
2. B: faults 0, есть ключи.
3. Оплатить заказ.

**Ожидание:** `delivered`, `seller_id = B`, один код. A не держит ключ.

**Сломано если:** коды списаны с A и B; два settlement.

**Разобрать:** [P8](#p8-fallback-после-таймаута) (здесь как раз **не** fallback на timeout).

---

### S8. Оба селлера недоступны

**Этап:** E3.

1. A и B `errorRate: 1`.
2. Оплатить.

**Ожидание:** `delivery_failed` (восстановимый), эскроу или `refund_pending`, **не** payable селлеру. HTTP заказа 200. Worker может ретраить.

**Сломано если:** 500 клиенту; статус потерян; селлеру начислили.

**Разобрать:** [P9](#p9-500-вместо-доменного-статуса), [P2](#p2-settlement-на-вебхуке).

---

### S9. Шторм 200 × 30 ключей

**Этап:** E4. **Учим:** гонка за инвентарь, не за один заказ.

1. Seed **30** ключей суммарно (A или A+B — зафиксировать).
2. Buyer `POST /storm { count: 200 }`.
3. Bank `POST /payments/batch` по всем orderId.
4. Reconcile. Grafana: keys_available → 0, out_of_stock растёт, 5xx плоский.

**Ожидание:** 30 `delivered` (или меньше, если часть не оплатилась — зафиксировать), остальные `out_of_stock`; ни один code на двух заказах; ledger: 30 settlement, 170 refund_pending (если все 200 paid).

**Сломано если:** 31+ выдач; 500 на «нет ключей»; 200 settlement; imbalance ≠ 0.

**Разобрать:** [P1](#p1-check-then-act), [P10](#p10-sold-out-это-500), [P11](#p11-нет-unique-на-code).

---

### S10. Оплачен, не выдан

**Этап:** E4.

1. Получить заказ в `out_of_stock` или `delivering` (оборвать селлера).
2. `GET /admin/reconcile`.

**Ожидание:** список «paid без code», деньги в escrow или refund_pending.

**Сломано если:** сверка пустая, а GET order не `delivered` при `paid` в событиях.

**Разобрать:** [P12](#p12-сверка-только-статусы-без-ledger).

---

### S11. Выдан, не оплачен (должно быть 0)

**Этап:** E4.

Прогнать S1–S9, затем reconcile-поле «delivered без paid».

**Ожидание:** пусто всегда.

**Сломано если:** есть строки — это дыра в FSM или ручная запись ключа.

**Разобрать:** [P15](#p15-выдача-до-paid).

---

### S12. Дожим после пополнения

**Этап:** E4.

1. S9, часть `out_of_stock`.
2. `POST seller /admin/keys/seed` ещё ключи.
3. `POST shop /admin/retry-stuck`.

**Ожидание:** часть заказов стала `delivered`, refund_pending уменьшился, settlement вырос, ключи не задвоены. Повторный retry безопасен.

**Сломано если:** двойная выдача на уже delivered; worker берёт один ключ на два заказа.

**Разобрать:** [P13](#p13-retry-без-блокировки).

---

### S13. Sold out не ошибка инфраструктуры

**Этап:** E4 + E5.

Повторить S9, смотреть Grafana HTTP и Kibana `level`.

**Ожидание:** 409 или тело заказа `out_of_stock`; метрика 5xx не скачет; лог Information, `reason=out_of_stock`.

**Сломано если:** красный error rate, exception в логах.

**Разобрать:** [P10](#p10-sold-out-это-500), [P16](#p16-oos-как-error-в-логах).

---

### S14. Цепочка логов по order_id

**Этап:** E5.

1. Happy path.
2. Kibana: `order_id: …`

**Ожидание:** buyer purchase → shop create → bank webhook → shop paid → seller issue → shop settle. Поля `event_id`, `request_id` на месте.

**Сломано если:** куски цепочки без общего id; разные форматы JSON, Logstash не парсит.

**Разобрать:** [P17](#p17-логи-без-корреляции).

---

### S15. Горячая витрина остатков

**Этап:** E6.

1. Seed >1000 SKU.
2. `GET /catalog/stock` много раз.
3. `EXPLAIN` в Postgres.

**Ожидание:** Index Scan / Bitmap по индексу остатков, стабильная latency. В записке — план.

**Сломано если:** Seq Scan по всей таблице на каждый запрос витрины.

**Разобрать:** [P18](#p18-остаток-считается-count-без-индекса).

## Проблемы разобрать

### P1. Check-then-act

`if (order.status == paid) return;` потом выдача без блокировки строки.

Два вебхука оба видят `created` → две выдачи. Лечится `UNIQUE(event_id)` + `SELECT FOR UPDATE` (или эквивалент) в одной транзакции с переходом статуса.

### P2. Settlement на вебхуке

На `paid` сразу `seller +X`. При 200 оплатах и 30 ключах селлерам уйдёт лишнее либо 170 оплат «исчезнут».

Вебхук только эскроу. Селлеру — после уникального ключа.

### P3. Нет UNIQUE event_id

Повтор вебхука — вторая обработка. At-least-once у платежек — норма. Идемпотентный ключ события — обязателен.

### P4. Идемпотентность только event_id

Разные event_id, один заказ, уже `delivered` — всё равно нельзя выдавать снова. Нужен терминальный статус + «повтор оплаты не меняет финал».

### P5. Вебхук 500, если заказа нет

Банк будет долбить. Либо 200 + буфер события, либо 200 «принято, заказа нет» с записью. Не 5xx на ожидаемый out-of-order.

### P6. Таймаут = отказ

Клиент оборвал HTTP, селлер уже зарезервировал code. Shop идёт к B → второй ключ, первый «сирота». Повтор с **тем же** `request_id` на A.

### P7. Новый request_id на retry

Селлер считает это новой выдачей. Стабильный `request_id` на заказ (например `req_{orderId}-1`).

### P8. Fallback после таймаута

Timeout — неизвестность, не отказ. B только после явного 4xx/5xx от A без выдачи. Иначе двойная выдача.

### P9. 500 вместо доменного статуса

`delivery_failed` / `out_of_stock` — бизнес. Клиент GET 200 + статус. 5xx — Postgres лёг, баг, таймаут **нашего** процесса.

### P10. Sold out это 500

Ломает Grafana и смысл мониторинга. 409 на создание/шторм или 200 GET с `out_of_stock`.

### P11. Нет UNIQUE на code

Два заказа, один ключ — классика гонки инвентаря. Constraint + `SKIP LOCKED`.

### P12. Сверка только статусы без ledger

Статусы сошлись, деньги нет. Сверять проводки: `bank = escrow + payable + fee + refund`.

### P13. Retry без блокировки

Worker и вебхук одновременно дожимают. Тот же FOR UPDATE / уникальный settlement idempotency_key `settle:{orderId}`.

### P14. Выдача внутри HTTP вебхука без outbox

Вебхук должен ответить быстро. Долгий `/issue` → банк ретраит → гонка. Событие committed, выдача в worker/outbox.

### P15. Выдача до paid

Селлер вызван из `created`. Нарушение S11. Выдача только из `paid`/`delivering`.

### P16. OOS как Error в логах

Kibana «всё красное», алерт врёт. Information + reason.

### P17. Логи без корреляции

Не собрать инцидент. Обязательны `order_id`, `event_id`, `request_id`, `service`.

### P18. Остаток считается COUNT без индекса

Витрина под нагрузкой умрёт. Денормализация остатка или индекс под предикат «в наличии».

### P19. Комиссия не в ledger

`amount` селлеру = полный платёж, площадка «в уме». Потом сверка не сходится с бизнесом. Fee — отдельный счёт.

### P20. ИИ закрыл тест моком времени

Тест 50 вебхуков «последовательно в одном lock» не ловит гонку. Нужны реальные параллельные HTTP (burst банка или Parallel.For).
