## 1. Топология (целевая)

Клиенты → Buyer → Shop → Seller A/B. Bank эмулирует эквайринг (вебхук). Shop владеет заказами, ключами площадки в ledger и сверкой. Селлер владеет пулом кодов. Банк денег внутри ledger не двигает — только событие `paid`/`failed`.

```
Postman
  ├─ Buyer.Api     :8081   POST /purchases, POST /storm          ← с E1b / E4b
  ├─ Shop.Api      :8080   заказы, webhook, reconcile, retry      ← с E0
  ├─ Bank.Api      :8082   POST /payments, /burst, /batch         ← с E1c / E2 / E1e
  ├─ Seller A      :8083   POST /issue, admin keys/faults         ← с E1d
  └─ Seller B      :8084   то же, fallback                        ← с E3b
Shop ── PostgreSQL :5432                                          ← с E0
все сервисы ── Logstash :5000 ── Elasticsearch :9200 ── Kibana    ← логи Shop с E0; остальные по мере появления
Shop (+sellers) ── Prometheus :9090 ── Grafana :3000              ← дашборды на E5
```

Compose **растёт**: этап добавляет сервис в тот же `deploy/docker-compose.yml`, не переписывает «пять контейнеров с нуля».

Деньги:

1. Вебхук `paid` → `BankAsset +X` / `Escrow +X`.
2. Уникальная выдача ключа → `Escrow −X` / `SellerPayable +(X−fee)` / `PlatformFee +fee`.
3. Нет ключа → `Escrow −X` / `RefundPending +X`. Селлеру ничего.

Списание клиенту / начисление селлеру — **settlement после выдачи**, не единственная проводка в момент вебхука.

Пустой остаток: статус `out_of_stock` или HTTP **409**, в логах Information, **не 500**.

## 2. Инварианты (после любой гонки)

1. `SUM(debit) = SUM(credit)` по `ledger_entries`.
2. Число `delivered` = число keys с `order_id` (факт выдачи в Shop).
3. Один `code` — один заказ. Один `event_id` — одна обработка платежа.
4. `bank_captured = escrow + seller_payables + platform_fees + refund_pending`.
5. Нет `delivered` без `paid`. Нет двух кодов на один заказ.
6. 50 вебхуков на один заказ → одна выдача.
7. 200 покупок × 30 ключей → 30 `delivered`, остальные `out_of_stock`, без всплеска 5xx.

### 3.2 Сущности Shop (Postgres)

| Сущность | Смысл | Поля и дефолты | Зачем дальше |
| --- | --- | --- | --- |
| **Product** | Товар витрины. Цена фиксируется **в заказе** в момент create, чтобы вебхук с чужой суммой не «переценил» покупку (S16). | 12 SKU из ТЗ на E1a. Валюта `RUB` (переключатель $ / ₸ в макете — только UI, не считаем). Типы `topup` / `key` / `subscription` / `giftcard` в лабе **одинаковы**: все выдают `code`. | E1a seed и выбор SKU для S1 (`STEAM-TOPUP-500` = 500 ₽, удобный счёт). E4b шторм — **другой** SKU `KEY-CS2-PRIME` (1290 ₽), чтобы цифры сверки не путать с «пятёрками». E6 — тысячи строк + индекс витрины. |
| **Order** | Намерение купить один SKU. Владеет FSM, снимком цены, стабильным ключом выдачи. | `sku`, `amount` (снимок цены), `status=created`, `request_id` вида `req_{orderId}:A` (повтор к A с тем же id), при fallback `req_{orderId}:B`, `seller_id`, `code`. | Вся лаборатория. E1e/S20 — 5 заказов. E4b — 200. `Idempotency-Key` на create (S18): двойной клик ≠ шторм (шторм — **разные** ключи). |
| **PaymentEvent** | Утверждение банка «деньги двинулись». Доставка at-least-once, порядок не гарантирован. | `event_id UNIQUE`, `order_id`, `status` `paid`\|`failed`, `amount`, `currency`, `created_at`. Строка **может появиться до заказа** (S5). | E1c — один вебхук. E2 — burst 50. S16 — amount ≠ цены заказа: 200, FSM не двигаем. S17 — `failed` после `paid`: игнор перехода. |
| **ShopKeys / факт выдачи** | Не пул «сырых» ключей. Это **факт**: какой `code` ушёл в какой заказ. Source of truth пула до `/issue` — **селлер**. | `code UNIQUE`, `order_id UNIQUE NULL`. | Инвариант «один code — один заказ» в Shop. S19: если A и B выдадут один литерал — UNIQUE взорвётся, так и должно. |
| **LedgerEntry** | Журнал денег, только append. Не апдейтим и не удаляем строки. | `idempotency_key UNIQUE`. Счета ниже. | S1 — три фазы (эскроу → settlement). S9 — бумага 200×1290. S12 — сторно `RefundPending`, не повтор из пустого эскроу. Сверка E4a без журнала — ложь (P12). |
| **Outbox** | «Выдать ключ **после** коммита вебхука». Чтобы HTTP банку был коротким. | Запись: заказ к выдаче. Worker читает. | С **E1d**, не «потом на гонках». Иначе S3 учит не тому (P14). `POST /admin/retry-stuck` на E4a дожимает те же строки. |

### 3.3 Счета ledger

| Счёт | Смысл | Когда двигается | Типичная ошибка |
| --- | --- | --- | --- |
| `bank_asset` | «Эквайринг сказал, что X пришло». Живого банка нет — это **наш** учёт поступления. | Вебхук `paid` с совпавшим amount: +X. | Двигать на `failed` или на чужой amount (S16). |
| `escrow` | Обязательство площадки: товар **или** деньги клиенту. Не доход селлера. | `paid`: +X. Выдача: −X. Нет ключа: −X в `refund_pending`. | Settlement селлеру отсюда **на вебхуке** (P2) — сломает S9. |
| `seller_payable:{id}` | Сколько должны селлеру A или B после **уникальной** выдачи. | Только после code: +(X−fee). Дожим S12: из `refund_pending`, не из пустого эскроу. | Начислить двум селлерам на один заказ (P8). |
| `platform_fee` | Комиссия площадки, **10%** amount, константа. Отдельный счёт, не «в уме amount−10%». | Вместе с payable при settlement. | P19: сверка «сошлась», бизнес — нет. |
| `refund_pending` | Оплачено, ключа нет. В лабе **не** возвращаем в банк (вне скоупа). Карман «должны клиенту». | OOS: +X из эскроу. S12 успех: −X → payable+fee. | Вторая проводка из эскроу после OOS (P22). |

Формула после любого прогона: `bank_asset = escrow + Σ payable + fee + refund_pending`.

### 3.4 Статусы заказа

| Статус | Смысл | Финал? | Кто ставит | Дальше |
| --- | --- | --- | --- | --- |
| `created` | Ждём оплату. Селлера **не** звать. | нет | Shop create | S2/S15 пути; S18 два created или один по Idempotency-Key |
| `paid` | Деньги в эскроу, можно выдавать. | нет | вебхук + сверка amount | outbox |
| `delivering` | Идёт `/issue`. | нет | worker | таймаут S6 — остаёмся здесь / ретрай A |
| `delivered` | Код привязан. Повтор оплаты не оживляет выдачу. | да | worker после уникального code | S4, S11, S17 |
| `payment_failed` | Банк сказал `failed` в `created`. | да | вебхук | S2; не путать с late failed (S17) |
| `out_of_stock` | Оплачено, пула нет. Восстановимый. Не 5xx. | нет | явный отказ селлера `out_of_stock` / пустой пул | S9, S12, S13 |
| `delivery_failed` | Оба селлера явно отказали (не timeout). Восстановимый. | нет | worker после A и B 5xx | S8, retry-stuck |

### 3.5 Сервисы как роли

| Сервис | Владеет | Не владеет | Появляется | Дефолты для тестов |
| --- | --- | --- | --- | --- |
| **Shop** | orders, payment_events, ledger, факт code, оркестрация, витрина | сырой пул до `/issue` | E0 | HTTP к селлеру timeout **2s** (короче sleep S6). Комиссия **10%**. |
| **Buyer** | ничего персистентного | деньги, ключи | E1b | `POST /purchases { sku }` — один покупатель. `POST /storm { sku, count }` — только E4b. Шторм ≠ Idempotency-Key. |
| **Bank** | генерация `event_id`, доставка вебхука | ledger | E1c | `/payments` — один заказ. `/payments/burst` — E2 (тот же / разные event_id). `/payments/batch` — список orderId (E1e на 5, E4b на 200). |

### 3.6 Идемпотентность — три разных ключа

| Ключ | Чей | Смысл | Где ломается без него |
| --- | --- | --- | --- |
| `event_id` | банк | одно событие оплаты | S3, P3 |
| `order_id` + терминальный статус | Shop | повторный paid ≠ вторая выдача | S4, P4 |
| `request_id` | Shop задаёт, селлер ключует пул | повтор после timeout = тот же code | S6, P6/P7 |
| `idempotency_key` проводки `settle:{orderId}` | ledger | worker и вебхук не начислят дважды | P13 |
| `Idempotency-Key` HTTP create | Buyer/Shop | двойной клик | S18, P24; в S20/S9 ключи **разные** |

### Shop REST

`POST /orders`, `GET /orders/{id}` — E1a.  
`POST /webhook/payment` — E1c.  
`GET /admin/reconcile`, `POST /admin/retry-stuck` — E4a.  
`GET /catalog/stock` — E6.  
`GET /health` — E0. `GET /metrics` — к E5.

FSM: `created → paid → delivering → delivered`; `payment_failed`; `out_of_stock` и `delivery_failed` восстановимые.

### Buyer REST

`POST /purchases { sku }` — E1b.  
`POST /storm { sku, count }` — E4b, не раньше: иначе пропускаем S20.

### Bank REST

Вебхук как в ТЗ (`event_id`, `order_id`, `status`, `amount`, `currency`, `created_at`).

`POST /payments` — E1c.  
`POST /payments/batch` — с E1e (сначала 5 id, потом 200).  
`POST /payments/burst` — E2 (дубли одного event_id **и** разные event_id на один заказ).

### Seller REST

`POST /issue { request_id, sku, order_id }` — тот же `request_id` → тот же code.  
`POST /admin/keys/seed`, `PUT /admin/faults { errorRate, timeoutRate, timeoutSeconds }`, `GET /admin/keys/available`.

Таймаут ≠ отказ: код мог быть зарезервирован до обрыва ответа. Shop не вызывает B, если A «неизвестно» (timeout); retry A с тем же `request_id`. B — если A явный 5xx/отказ; у B **свой** `request_id` (`:B`).

## 5. Данные (Postgres)

Владелец доменных таблиц ниже — **Shop**. У селлера — свой пул (отдельная БД или схемы `seller_a` / `seller_b` на том же инстансе). Не два инвентаря одного code в Shop и у селлера.

- `products` — SKU ТЗ; на E6 тысячи строк + индекс витрины остатков.
- `orders` — sku, amount, status, request_id, seller_id, code.
- `payment_events` — `event_id UNIQUE`, можно появиться **до** заказа.
- факт выдачи (таблица или уникальность на `orders.code`) — `code UNIQUE`.
- `ledger_entries` — append-only, `idempotency_key UNIQUE`.
- `outbox` — выдача после коммита вебхука, worker читает.

## 6. Наблюдаемость

- Serilog JSON → Logstash TCP → ES `shop-*` → Kibana (`service`, `order_id`, `event_id`, `request_id`, `reason`). С E0 есть хотя бы `service=shop`.
- Prometheus + Grafana на **E5**: статусы заказов; `keys_available`; HTTP 2xx/409/5xx; `ledger_imbalance=0`.
- ES однонодовый, heap ~1 GB.

До E5 гонки смотрим тестами, SQL reconcile (с E4a) и Kibana по `order_id`.

## 9. Правила для агента

1. Сначала этот файл, потом код. Статус задачи менять здесь же.
2. Не поднимать «сразу пять API». Новый процесс — отдельный этап с health + тестом.
3. Не пропускать E2 и E3a/E3b «потом поправим» — там ядро обучения.
4. Не прыгать на шторм, пока нет `done` у E1e (S20) и E4a (сверка на малом).
5. Не ставить 500 на sold out.
6. Новый контракт REST — строка в §4 и задача в §8.
7. Часы в §7 — потолок этапа; если разъехалось — обновить §7.
8. Этап обучения не `done`, пока не прогнаны его сценарии из [обучение/сценарии.md](обучение/сценарии.md), не разобраны P и не записаны ответы на «вопросы себе» в файле этапа.
9. Вводя сущность, поле или дефолт — строка в §3 (смысл + где пригодится), не только в чате.

## 10. Решения, которые закрываем по умолчанию

Подробности и остаток дыр: [обучение/пробелы.md](обучение/пробелы.md). Пока не оспорено:

- Пул ключей до выдачи только у селлера; в Shop — факт выдачи и `UNIQUE(code)`.
- Пулы A и B не пересекаются. Разрез пула ТЗ: A — голова (S1 + 30 шторма), B — хвост.
- `request_id`: `req_{orderId}:A` и `req_{orderId}:B` — стабильные и разные.
- Дожим S12: `RefundPending → payable + fee` (P22).
- Выдача с E1d через outbox/worker, вебхук быстрый.
- .NET 9, комиссия 10%, шторм на одном SKU `KEY-CS2-PRIME`, 30 ключей на A, timeout клиента 2s.
- Вебхук с чужим amount: 200, без смены статуса (S16).
- `failed` после `paid`: игнор перехода (S17).
- Лестница тестов: один покупатель → S20 (5 параллельных) → шторм. `/storm` не делать на E1b.
